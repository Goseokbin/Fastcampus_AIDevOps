# 요구사항: 쇼핑몰 dev 장애 대응 — 알람 뒤 첫 5분

> 플랫폼팀 · 결제 서비스 오너 · 당번(on-call) 회의에서 정한 내용. 결정되지 않은 것은 "미정" 으로 남겼다.
> 이 메모로 만드는 것: 첫 Runbook(`docs/runbooks/`), 알람 → Runbook 연결, CLAUDE.md 의 장애 대응 규칙.
> 관측 · SLI · 알람은 `specs/observability.md` 를 그대로 쓴다(지금 import 된 스펙). 새 작업 스펙은 만들지 않는다.

## 배경

- 관측 스택(Part 4)으로 "지금 주문이 되는가 · 어디서 깨졌는가" 는 답할 수 있다. 주문 실패 알람(`OrderFailureRateHigh`)도 있다.
- 그런데 알람이 울리면 당번은 어디서부터 볼지 매번 처음부터 생각한다. 알람에는 Runbook 링크가 없고, 예전 Runbook 은 위키에 있어 아무도 고치지 않았다.
- 지난 장애 연습에서 결제가 실패하는 동안 email Pod 도 재시작하고 있었다. 두 사람이 email 을 원인으로 보고 20분을 썼다. 동시에 일어난 다른 문제에 속은 것이다.
- Claude 는 관측 데이터를 읽기 전용으로 조회할 수 있다(`/obs-ask`). 하지만 알람을 받았을 때 어떤 순서로 무엇을 내고 어디서 멈추는지는 정한 적이 없다.

## 목적 (결정)

- 알람이 울리면 **5분 안에** 근거가 붙은 첫 보고가 나온다: 영향 범위 · 심각도 제안 · 원인 후보(근거와 반증) · 사람이 정할 것.
- 사람과 Claude 가 같은 Runbook 을 읽고 같은 순서로 본다. Runbook 은 알람에서 바로 열린다.
- Claude 는 **선분석**(증거 · 제안), 사람은 **결정**(선언 · 심각도 확정 · 복구 실행 · 공지 · 종료).

## 역할 (결정)

- 장애 지휘자(IC): 그날 당번. dev 는 @TeddySB2. 장애 선언 · 심각도 확정 · 복구 승인 · 종료 선언을 한다.
- Claude: 조사만 한다. 결정이 필요한 곳에서 멈추고 "IC 가 정할 것" 을 목록으로 보인다.

## 심각도 (결정)

사용자 영향으로 가른다. 처음 매긴 값은 임시이며, 영향 범위가 확인되면 IC 가 바꾼다.

| 심각도 | 기준 (쿼리는 `specs/observability.md` 9장 SLI-1) | 대응 |
| --- | --- | --- |
| SEV1 | 5분 주문 실패율 50% 이상, 또는 주문이 전혀 처리되지 않음 | IC 즉시 · 장애 선언 |
| SEV2 | `OrderFailureRateHigh` firing, 또는 5분 주문 실패율 5% 이상 | IC 즉시 |
| SEV3 | 주문은 정상, 다른 기능 일부 오류(상품 · 광고 · 추천) | 업무 시간 · Issue |
| SEV4 | 사용자 영향 없음 (재시작 후 정상 · 알람만) | 기록 |

## Claude 가 하는 것 · 하지 않는 것 (결정)

- 한다: 읽기 전용 조회(Grafana MCP, `kubectl get/describe/logs/events`, `argocd app get/history`), 영향 범위 · 심각도 제안, 원인 후보 표(근거 · 반증 · 확신), 복구 후보 정리(실행하지 않음).
- 하지 않는다: 장애 선언, 심각도 확정, 복구 실행(클러스터 변경 · 플래그 변경 · revert merge), 공지.
- 원인 후보는 최소 두 개. 지지하는 근거보다 반증을 먼저 찾는다. 같은 시각에 다른 문제가 있으면 "관련 없음" 의 근거를 적는다.
- 증거가 모자라면 단정하지 않고 "모름" 과 확인 방법을 적는다. 플래그 상태는 Claude 가 볼 수 없으므로 사람이 확인해 알려 준다.

## 시간 (결정, dev)

- 첫 보고 5분, 이후 10분마다 같은 형식으로 갱신. 30분이 지나도 원인 서비스를 못 좁히면 IC 에게 알리고 다음을 묻는다.

## Runbook (결정)

- 위치: `docs/runbooks/<알람 이름 또는 증상>.md`. 위키가 아니라 저장소에 두고 PR 로 고친다.
- 알람에서 바로 열린다: PrometheusRule 의 `annotations.runbook_url` 에 GitHub 의 파일 주소를 넣는다.
- 첫 Runbook 은 `OrderFailureRateHigh`. 지금 울리는 알람이 이것 하나다.
- 사람과 Claude 가 그대로 따라 할 수 있어야 한다. 그래서 Runbook 에는 다음이 들어간다.
  - 이 알람이 뜻하는 것 (단계별 burn rate)
  - 먼저 볼 것과 **쿼리 원문** (순서대로, 수집 확인부터)
  - 판단 기준 (심각도 표, "이 값이면 이쪽" )
  - 흔한 함정 (동시에 일어난 다른 문제, 데이터 없음)
  - 복구 후보와 누가 실행하나 (실행은 사람)
  - 멈추고 IC 에게 물을 곳
- 장애가 끝나면 이번에 막힌 곳을 Runbook 에 반영한다.

## 대상과 제약 (결정)

- 대상은 `otel-demo-dev` 만. `otel-demo-prod` 는 관측 스택이 없다.
- 장애 주입(`scenarios/flag.sh …`)은 사람이 한다(팀 규칙 예외, 승인자 @TeddySB2). 연습에서도 Claude 는 플래그를 보거나 바꾸지 않는다.
- 클러스터와 AWS 는 Claude 가 바꾸지 않는다. 복구 실행 경로와 승인은 다음 작업에서 정한다.

## 이번 작업에서 하지 않는 것 (결정)

- 복구 실행과 승인 체계, 장애 전파 · 타임라인 · 포스트모템 (다음 작업들)
- 다른 알람의 Runbook (장애를 겪으면서 하나씩 늘린다)
- Alertmanager 수신처
